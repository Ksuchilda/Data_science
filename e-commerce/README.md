# E-commerce User Behavior Analytics, Purchase Prediction & Recommendation System

Проект по анализу поведения пользователей e-commerce платформы на данных **Retail Rocket Dataset**.  
Ноутбук объединяет продуктовую аналитику, ML-модель предсказания покупки, кластеризацию пользователей, рекомендательную систему и пример production-deployment через FastAPI.

## Цель проекта

Построить end-to-end систему, которая помогает бизнесу:

- анализировать путь пользователя от просмотра товара до покупки;
- находить точки потерь в воронке `view → addtocart → transaction`;
- предсказывать вероятность будущей покупки пользователя;
- сегментировать пользователей по поведению;
- формировать персональные рекомендации;
- использовать результаты модели для ретаргетинга и маркетинговых решений.

## Данные

Используется **Retail Rocket Dataset** [https://www.kaggle.com/code/johnosorio/retail-rocket-ecommerce-recommender-system] — набор событий e-commerce платформы примерно за 4.5 месяца.


| Файл | Описание | Ключевые поля |
|------|----------|---------------|
| `events.csv` | Лог действий пользователей | `timestamp`, `visitorid`, `event`, `itemid`, `transactionid` |
| `item_properties_part1/2.csv` | Динамические свойства товаров | `timestamp`, `itemid`, `property`, `value` |
| `category_tree.csv` | Структура каталога | `categoryid`, `parentid` |

Поле `event` принимает три значения: `view`, `addtocart`, `transaction`.

## Основные этапы

### 1. Подготовка данных

- загрузка событий, свойств товаров и дерева категорий;
- объединение файлов `item_properties_part1` и `item_properties_part2`;
- проверка пропусков, дубликатов и типов данных;
- приведение `timestamp` к формату `datetime`;
- создание бинарного признака покупки `is_purchase`;
- сортировка событий по времени.

### 2. EDA и продуктовая аналитика

В проекте анализируются:

- распределение событий `view`, `addtocart`, `transaction`;
- товарная воронка;
- пользовательская активность;
- популярность товаров;
- покупки и конверсия;
- временные паттерны поведения по часам и дням недели.

Ключевые выводы:

- просмотры составляют около **96.68%** всех событий;
- добавления в корзину — около **2.6%**;
- покупки — около **0.81%**;
- до покупки доходят примерно **0.83%** пользователей, просмотревших товары;
- событие `addtocart` является сильным сигналом будущей покупки.

### 3. Статистический анализ

Проведены статистические проверки:

- **Mann–Whitney U test** — будущие покупатели активнее по числу событий, уникальных товаров и активных дней;
- **Chi-square test** — добавление товара в корзину существенно связано с вероятностью покупки.

### 4. Feature Engineering

Для модели создаются пользовательские, товарные, временные и категорийные признаки:

- количество событий пользователя;
- количество просмотров, добавлений в корзину и покупок;
- число уникальных товаров и категорий;
- recency-признаки;
- средний час активности;
- популярность товаров;
- взаимодействие с корзиной;
- история покупок;
- признаки доступности товаров.

### 5. ML-модель предсказания покупки

Задача решается как бинарная классификация:

```text
1 — пользователь совершит покупку
0 — пользователь не совершит покупку
```

Использованные модели:

- Dummy baseline;
- Logistic Regression;
- Random Forest;
- LightGBM;
- LightGBM + SMOTE.

Основная проблема — сильный дисбаланс классов, поэтому accuracy не используется как ключевая метрика.

Основные метрики:

- ROC-AUC;
- PR-AUC;
- Precision;
- Recall;
- Lift.

Итоговая модель: **LightGBM**.  
Выбранный порог классификации: **0.90**.

Результаты на test-выборке:

| Model | ROC-AUC | PR-AUC | Precision | Recall | F1 |
|---|---:|---:|---:|---:|---:|
| LightGBM | 0.6697 | 0.0939 | 0.2162 | 0.1143 | 0.1495 |
| Logistic Regression | 0.8073 | 0.0686 | 0.0113 | 0.3571 | 0.0219 |

LightGBM лучше подходит для точечного ретаргетинга, так как выделяет меньший, но более качественный сегмент пользователей.

### 6. Интерпретация модели

Для интерпретации используется **SHAP-анализ**.

Важные признаки модели:

- `recency_x_unique_cats`;
- `user_max_item_popularity`;
- `user_avg_item_popularity`;
- `user_avg_hour`;
- признаки корзины;
- история покупок пользователя.

### 7. Кластеризация пользователей

Пользователи сегментируются с помощью **KMeans**.  
Выбрано количество кластеров: **k = 6**.

| Сегмент | Кластер | Доля | Стратегия |
|---|---:|---:|---|
| Случайные посетители | 0 | 64.34% | Онбординг, промо, витрина топ-товаров |
| Активные исследователи | 1 | 1.91% | Персональные рекомендации, отзывы |
| Лояльные покупатели | 2 | 0.83% | Лояльность, upsell/cross-sell |
| Недавно активные | 3 | 11.06% | Мягкий ретаргетинг |
| Холодные посетители | 4 | 11.54% | Общие промо-акции |
| Пользователи с корзиной | 5 | 10.32% | Напоминание о корзине |

### 8. Рекомендательная система

Реализованы два подхода:

- **Item-Item Collaborative Filtering**;
- **Popularity-based baseline**.

Для матрицы взаимодействий используются веса:

```text
view = 1
addtocart = 3
transaction = 5
```

Результаты offline-оценки:

| System | HitRate@10 | Precision@10 |
|---|---:|---:|
| Item-Item CF | 0.280 | 0.028 |
| Popularity Baseline | 0.018 | 0.0018 |

Item-Item Collaborative Filtering значительно превосходит popularity baseline.

### 9. Business Decision Layer

Результаты аналитики, ML-модели, сегментации и рекомендаций объединяются в единую бизнес-логику.

Для пользователя формируется профиль:

- вероятность покупки;
- сегмент;
- уровень purchase intent;
- рекомендуемая бизнес-стратегия;
- персональные рекомендации товаров.

Пример функции:

```python
get_user_profile(visitor_id)
```

Она возвращает полный профиль пользователя для маркетинговых и продуктовых действий.

### 10. Production Deployment

В проекте реализован пример production-интеграции:

- сериализация модели через `joblib`;
- сохранение списка признаков;
- сохранение оптимального порога классификации;
- standalone inference-функция;
- FastAPI endpoint.

Пример endpoint:

```text
POST /predict
```

Вход:

```json
{
  "visitor_id": 12345
}
```

Выход:

```json
{
  "visitor_id": 12345,
  "purchase_proba": 0.87,
  "will_buy": false
}
```


## Ограничения проекта

- В датасете нет цен, демографии пользователей и подробных контентных признаков товаров.
- Offline-оценка рекомендаций не заменяет A/B-тест.
- Recall модели покупки остается низким из-за сильного дисбаланса классов.
- FastAPI-пример не подключен к реальной базе данных или streaming-источнику событий.
